# trajectory 截断策略的数据层面对比

> 所有数字来自 `python -m experiments.truncation.run` 的一次完整运行，原始结果在 `results/results.json`、`results/summary.md`（第 4 节的 72 个单元）和 `results/summary_allocation.md`（第 5 节的 54 个单元）。
>
> **2026-10-16 更正**：第 4.1 节中 `split_on_budget` 的大幅提升，主要来自该设置下单行允许的总长更大（prompt 32k + response 4k），而不是切分本身。在**同样的单行总长**下比较（第 5 节），切分保留的 policy token 从不多于截断。原有数字都保留不变，解读以第 5、6 节为准。本实验只比较训练数据本身，**没有做任何训练**，不能说明哪种策略的训练效果更好。

## 1. 研究问题

`trajectory` 聚合把多轮的生成（mask=1）和工具观察（mask=0）拼成一个 response。超出 `max_response_length` 时，默认做法是截掉尾部。尾部恰好是后几轮的生成，而奖励却按整条轨迹给出，这就产生了**信用分配错位**：一行带着整条轨迹的奖励，却可能已经不包含真正完成任务的那几步。

本实验回答：在真实轨迹的长度分布下，

1. 直接截断会丢掉多少 policy token？有多少条轨迹的最后一次生成被截掉？
2. `split_on_budget`（按轮次边界另起一行）和 `drop`（整行丢弃）能改善多少？各自的代价是什么？

## 2. 设置

- **数据与事件**：复用前缀一致性实验的同一批样本（SWE-smith、Toucan、nebius SWE-agent 各 300 条，种子 0，每条最多 50 轮，见 [`../template_prefix/DATA.md`](../template_prefix/DATA.md)），用 Qwen2.5-7B-Instruct tokenizer 和 B 方式（vLLM token id）构造事件。这个组合 100% 前缀合并，所以 trajectory 行就是完整轨迹。
- **策略**（`build_samples(truncation_strategy=...)`）：
  - `truncate`（默认）：截掉尾部。
  - `split_on_budget`：并入下一轮会超出上限时，在轮次边界另起一行，新行的 prompt 是到此为止的完整上下文；单轮生成本身超限时仍截断。
  - `drop`：超限的行整行丢弃。
- **长度网格**：`max_prompt_length` ∈ {8192, 32768}，`max_response_length` ∈ {4096, 8192, 16384, 32768}。
- **指标**：只统计没被 `is_drop` 标记的可用行。
  - **policy 保留率**：可用行里的 policy token 数 ÷ 轨迹中全部生成 token 数。
  - **最终生成丢失**：轨迹最后一轮的生成没有完整出现在任何可用行里的轨迹占比。
  - **行尾仅观察**：response 最后一个 token 是观察 token 的可用行占比。
  - **行 token 总量**：可用行的 prompt + response token 总数，近似反映前向计算量。

## 3. 长度分布：预算主要被观察占用

| 数据集 | 平均轮数 | 合并 response 长度 p50 / p90 / max | 生成 token 占合并 response 的比例 |
|---|---:|---:|---:|
| SWE-smith | 19.05 | 12,407 / 38,322 / 88,438 | 16.7% |
| nebius SWE-agent | 21.49 | 8,793 / 28,366 / 34,596 | 17.9% |
| Toucan | 2.40 | 343 / 4,021 / 39,426 | 20.7% |

在三个数据集里，合并 response 中**约 80% 是工具观察**（mask=0）。response 预算主要被观察消耗，而不是被模型生成消耗。

## 4. 结果

### 4.1 prompt 预算充足（`max_prompt_length = 32768`）

| 数据集 | max_response | policy 保留率 truncate → split（drop） | 最终生成丢失 truncate → split | truncate 行尾仅观察 | split 行数/轨迹 | split ÷ truncate 行 token 总量 |
|---|---:|---|---|---:|---:|---:|
| SWE-smith | 4,096 | 9.4% → **84.7%**（1.2%） | 95.7% → **13.3%** | 86.7% | 3.98 | 8.82× |
| SWE-smith | 8,192 | 26.4% → **85.8%**（9.1%） | 75.0% → **11.7%** | 59.7% | 2.48 | 3.69× |
| SWE-smith | 16,384 | 57.2% → **85.3%**（33.2%） | 36.7% → **11.7%** | 30.7% | 1.55 | 1.75× |
| SWE-smith | 32,768 | 84.1% → 86.0%（61.0%） | 13.7% → 12.7% | 9.0% | 1.15 | 1.01× |
| nebius | 4,096 | 34.9% → **99.6%**（4.9%） | 83.7% → **1.7%** | 69.0% | 3.44 | 7.77× |
| nebius | 8,192 | 55.0% → **99.9%**（19.2%） | 54.0% → **0.7%** | 44.7% | 2.04 | 3.57× |
| nebius | 16,384 | 77.8% → **99.7%**（41.8%） | 31.7% → **1.3%** | 25.3% | 1.33 | 1.71× |
| nebius | 32,768 | 99.7% → 99.7%（96.4%） | 1.3% → 1.3% | 1.3% | 1.01 | 1.00× |
| Toucan | 4,096 | 84.4% → **99.9%**（78.9%） | 9.0% → **0.3%** | 7.7% | 1.09 | 1.42× |
| Toucan | 32,768 | 99.9% → 99.9%（99.8%） | 0.3% → 0.3% | 0.3% | 1.00 | 0.96× |

- **truncate 的损失集中在轨迹尾部。** 例如 SWE-smith 在 `max_response_length = 4096` 时，95.7% 的轨迹丢了最后一次生成，86.7% 的行截断后结尾只剩观察 token。
- **split_on_budget 基本消除了尾部损失**（注意：split 的行 prompt 最长可到 32,768，单行总长远大于 truncate 行，见第 5 节）：nebius 的 policy 保留率在所有预算下都 ≥ 99.6%，最终生成丢失 ≤ 1.7%。SWE-smith 的保留率停在约 85%，剩下的损失来自少数超长轨迹：后段行的 prompt 超过 32,768，被标记为 `is_drop`（4,096 预算下有 140 行）。
- **代价是计算量**：新行重复携带完整历史，response 预算越小，行 token 总量越大，4,096 预算下 SWE-smith 是 8.82×、nebius 是 7.77×。预算达到 32,768 时，两种策略几乎没有差别。
- **drop 最差**：不仅丢掉的 policy token 最多，还会整条丢弃长轨迹。SWE-smith 在 4,096 预算下 95.7% 的轨迹没有任何可用行，这会让训练数据系统性地偏向短轨迹。

### 4.2 prompt 预算紧张（`max_prompt_length = 8192`）

| 数据集 | max_response | policy 保留率 truncate / split | split 产生的 `is_drop` 行 |
|---|---:|---|---:|
| SWE-smith | 4,096 | 9.4% / 29.5% | 665 |
| SWE-smith | 8,192 | 26.3% / 26.0% | 443 |
| SWE-smith | 16,384 | 57.0% / 56.5% | 165 |
| nebius | 4,096 | 34.9% / 55.6% | 491 |
| nebius | 8,192 | 55.0% / 54.8% | 311 |
| nebius | 16,384 | 77.8% / 77.4% | 99 |

prompt 预算紧张时，split 产生的后段行 prompt 太长，大量被标记为丢弃。只有在最小的 response 预算下还有一定提升，预算达到 8,192 以后就和 truncate 持平，甚至略低。**split_on_budget 是否有效，取决于 prompt 预算能不能容纳轨迹后段的完整上下文。**

## 5. 补充实验：同一单行总长下的预算分配（方案 1）与共享前缀成本（方案 2）

### 5.1 为什么要补这组实验

第 4 节里，truncate 和 split 的单行总长上限并不相同：truncate 只有一行，长度是首轮 prompt 加上 response 上限；split 的后段行 prompt 最长可以到 `max_prompt_length`。两者的比较不公平。

在单行总长上限为 T 的约束下，可以证明：完整序列中位置 ≥ T 的生成 token，任何一行都装不下，除非截断历史，而截断历史会改变上下文。truncate 已经覆盖了位置 < T 的全部内容，所以在相同的 T 下，切分不可能保留更多 policy token。

**方案 1**：固定单行总长 T ∈ {8k, 16k, 32k}，对比两种分配方式：
- `fixed_half`：prompt 和 response 各 T/2；
- `dynamic_total`：prompt 和 response 的上限都是 T，同时 `max_total_length = T`。

**方案 2**：用 `trace2batch.core.shared_prefix_lengths` 统计相邻行的共享前缀，得到"共享前缀只算一次"时的去重 token 数。

### 5.2 方案 1 结果：动态分配显著提高保留率，切分没有额外收益

| 数据集 | 单行总长 T | truncate 保留率（fixed → dynamic） | 最终生成丢失（fixed → dynamic） | split 保留率（fixed / dynamic） |
|---|---:|---|---|---|
| SWE-smith | 8,192 | 9.4% → **22.4%** | 95.7% → 81.0% | 9.1% / 22.4% |
| SWE-smith | 16,384 | 26.3% → **54.6%** | 75.0% → 41.3% | 26.0% / 54.6% |
| SWE-smith | 32,768 | 57.2% → **83.0%** | 36.7% → 14.3% | 57.3% / 83.0% |
| nebius | 8,192 | 34.9% → **45.1%** | 83.7% → 63.3% | 34.1% / 45.1% |
| nebius | 16,384 | 55.0% → **73.5%** | 54.0% → 36.3% | 54.8% / 73.5% |
| nebius | 32,768 | 77.8% → **99.4%** | 31.7% → 2.0% | 77.4% / 99.4% |
| Toucan | 8,192 | 79.3% → **88.1%** | 13.3% → 8.7% | 78.1% / 88.1% |
| Toucan | 16,384 | 89.9% → **92.1%** | 6.0% → 3.3% | 89.7% / 92.1% |
| Toucan | 32,768 | 93.0% → **98.6%** | 3.0% → 0.7% | 94.1% / 98.6% |

- **在相同的单行总长下，把固定对半分改成动态分配，truncate 的 policy 保留率在所有设置下都提高了**。最大的是 SWE-smith T=16k，从 26.3% 提到 54.6%，约翻倍；最终生成丢失从 75.0% 降到 41.3%。原因是首轮 prompt 通常很短（SWE-smith p50 为 652），固定的 T/2 prompt 额度大部分闲置，动态分配把这部分让给了 response。
- **split 在相同的 T 下从不多保留 policy token**：动态分配时与 truncate 完全相同，固定分配时持平或略低（比如 SWE-smith T=8k 时 9.1% 对 9.4%），与 5.1 的推导一致。
- split 剩下的价值是**行边界干净**：在所有设置下，"行尾仅观察"的比例都是 0%，而 dynamic truncate 是 0.3%–63.5%。行在轮次边界结束，不会截在一次生成或观察的中间。
- 局限：动态分配要求训练端按总长打包序列（例如 verl 的 remove-padding），而不是把 prompt 和 response 分别 pad 到各自的上限；否则显存仍按 prompt 上限 + response 上限计算。

### 5.3 方案 2 结果：split 的计算膨胀大部分是重复前缀

第 4.1 节的设置（prompt 32k）下，split 相对 truncate 的 token 倍数：

| 数据集 | response 预算 | 行 token 总量倍数 | 去重后倍数 | 共享前缀占 split 行 token 的比例 | 每个保留的 policy token 需要的 token 数：truncate / split / split 去重 |
|---|---:|---:|---:|---:|---|
| SWE-smith | 4,096 | 8.82× | **3.29×** | 62.6% | 17.4 / 17.1 / **6.4** |
| SWE-smith | 16,384 | 1.75× | **1.29×** | 26.6% | 7.5 / 8.8 / **6.4** |
| nebius | 4,096 | 7.77× | **2.51×** | 67.7% | 7.4 / 20.2 / **6.5** |
| nebius | 16,384 | 1.71× | **1.25×** | 26.7% | 6.6 / 8.9 / **6.5** |

- 4k 预算下，split 行 token 的 62.6%（SWE-smith）和 67.7%（nebius）是与上一行重复的前缀。
- 去重后的倍数仍然大于 1，是因为 split 确实保留了更多内容（保留率 84.7% 对 9.4%）。按"每个保留下来的 policy token 需要处理多少 token"来算，去重后的 split 是 6.4–6.5，低于或接近 truncate 的 6.6–17.4。
- 局限：这只是成本核算。要真正省下这部分计算，训练端需要支持共享前缀的 attention 或 prefix cache，本项目没有实现。

## 6. 结论（更新于 2026-10-16）

1. 在真实的代码 Agent 轨迹上，常见的 4k–16k response 预算会让默认截断丢失大量后期生成：SWE-smith 在 4,096 预算下 policy 保留率只有 9.4%，在 16,384 预算下仍有 36.7% 的轨迹丢失最后一次生成。
2. 预算主要被工具观察占用（约 80%）。截断之后，很多行的结尾只剩观察 token。
3. **真正的约束是单行总长。** 在相同总长下，"prompt / response 动态分配"是最有效的改进，truncate 的保留率提高到 1.02–2.38 倍（例如 SWE-smith T=16k 时从 26.3% 到 54.6%）；切分不会额外保留 policy token，只能保证行在轮次边界结束。
4. 第 4 节中 split 的大幅提升，来自它使用了更大的单行总长。split 的 token 膨胀中，62.6%–67.7%（4k 预算）是重复前缀；如果训练端支持共享前缀计算，每个保留 policy token 的成本与 truncate 相当甚至更低。
5. `drop` 在所有设置下都不如另外两种，并且会系统性地丢掉长轨迹。
6. 超过单行总长的那部分轨迹，只有修改上下文（例如压缩工具观察，即方案 3）才能保留，但这会带来 off-policy 风险，需要训练来验证。

## 7. 局限性

- **没有训练实验。** 保留更多 policy token、避免尾部丢失，是否能带来更好的训练效果，需要 GPU 上的对比训练来验证（P3，不在本次范围内）。
- split 之后，每一行仍然使用整条轨迹的奖励，只是保证了每个动作都出现在某一行里，**并没有解决按步骤分配信用的问题**。
- 结果只基于 Qwen2.5 tokenizer 和 3 个数据集的各 300 条轨迹，每条最多 50 轮。轮数更多的轨迹截断会更严重，这里没有覆盖。
- 行 token 总量只是计算量的粗略代理，没有考虑 padding、attention 的二次复杂度和 prefix cache。
