# P3-A 报告：逐轮与合并样本的真实训练成本

> 所有数字都来自真实运行（Kaggle T4）。结果数据在 [`results/`](results/)，各节注明对应文件；pilot 的数字只在本报告中给出。

## 1. 研究问题

多轮 Agent 轨迹在 trajectory 合并失败时会退化为逐轮表示（transition）：同样的 policy token 被拆成多行，每一行都要带上此前的完整上下文。P1 已经量化了这种退化在 token 数量上的膨胀；P3-A 要回答的是：**在真实训练循环里，它让耗时和显存增加多少？差距由什么决定？**

范围：masked cross-entropy + LoRA 的训练成本基准。不是 GRPO、完整 RL 或全参数训练，也不评价模型能力或学习效果。

## 2. 方法

### 2.1 模型与训练设置

| 项目 | 设定 |
|---|---|
| 模型 | `Qwen/Qwen3-0.6B@c1899de2`，关闭思考，v2 前缀稳定模板 |
| 适配器 | LoRA r=8、alpha=16、dropout=0，作用于 q_proj／v_proj，bias none；可训练参数 1,146,880 |
| 精度与显存 | CUDA fp16 autocast + GradScaler；梯度检查点；关闭 KV cache；microbatch 1，无 padding |
| 优化 | AdamW，lr 1e-4；每条 rollout 累积所有行的梯度后**只更新一次**；loss 按该 rollout 的 policy token 数归一化 |
| 硬件 | Kaggle Tesla T4（单卡，可用 14.56 GiB），torch 2.11.0+cu128，Python 3.13.15 |

### 2.2 公平性设计

- 两种表示来自**同一份**规范 token 事件；数据审计逐个监督目标核对 token ID 与此前完整上下文都相同，不只比较 token 总数。
- 每个条件都从相同的 LoRA 初始参数和全新优化器开始；预热后再次重置；两次重复按 AB/BA 顺序交替，抵消顺序和漂移的影响。
- 计时包含张量构造、前向、masked loss、反向、有限性检查和更新，不包含模型加载与预热；CUDA 在前后同步。
- 每格先做一次**梯度核对**：两种表示的归一化 loss 和全部可训练梯度必须一致，否则不计时。核对在 training 模式下进行（保证梯度检查点生效），并使用 loss scale 4096；通过条件为 loss 相对误差 ≤1e-3、梯度相对 L2 ≤0.02、余弦 ≥0.9998。
- 速度比定义为 `transition 秒数 / trajectory 秒数`；只有所有条件都完整完成才计算。

### 2.3 数据

三个公开数据集（SWE-smith、Toucan-Qwen3、nebius SWE-agent），revision 与分片固定，每个数据集取 seed 0 的 300 条候选。

- **pilot**：每个数据集 4 条，取前 4 轮，完整上下文 ≤4096。
- **第一阶段（按长度分层）**：三层 (0, 2048]、(2048, 4096]、(4096, 6144]。每条候选取落在该层内的**最长完整轮次前缀**（不截断任何一轮，至少 2 轮，最多 20 轮）；从高层到低层按 seed 顺序挑选，同一条对话只用一次。每格 6 条，共 9 格、54 条 rollout、19,278 个 policy token。

样本都是轨迹的前缀片段，不是完整轨迹。

### 3.3 逐条 rollout 分析（54 条）

每个条件都记录了各条 rollout 的耗时（CUDA event），速度比按两次重复的平均值计算。

- 速度比为 1.03–5.11，中位数 1.91。
- **决定因素是处理 token 比，而后者主要由轮数决定。** 速度比与处理 token 比的相关系数为 0.978，与轮数为 0.895；与最终上下文长度只有 0.296。

|---:|---:|---|---:|
| 2 | 30 | 1.58（1.03–1.94） | 1.70 |
| 3 | 7 | 1.47（1.29–2.33） | 1.80 |
| 4 | 3 | 2.08（1.93–3.02） | 2.70 |

- **节省的时间小于节省的 token，而且差距随长度扩大。** 速度比 / 处理 token 比的中位数在 ≤2k、2–4k、4–6k 分别为 0.97、0.87、0.81（整体用 0.828 × token 比拟合，最大残差 0.69）。合并表示只剩一条最长的行，而在 T4 上每 token 的成本随长度上升：GQA 注意力在 torch 2.11 的 T4 上只能走 math 内核，计算量含平方项。所以合并带来的时间收益略低于 token 收益。
- **峰值显存两种表示基本相同。** 逐轮表示的最后一行带有完整上下文，与合并行一样长，峰值由最长行决定。差异体现在时间上，不在峰值显存上；约 6k token 时峰值约 10.5 GiB。

### 3.4 第二阶段：固定长度窗口，只改变轮数（32 格，192 条）

设计：SWE-smith 与 nebius × 轮数 2/4/6/8 × 窗口 (3072, 4096] 和 (4096, 5120] × 两个独立样本组（seed 0、seed 1），每格 6 条，取恰好 k 轮的完整前缀；所有格、两个组之间不重复使用同一条对话。训练与计时设置与第一阶段相同；四次提交 A（seed 0，3–4k）、B（seed 1，3–4k）、C（seed 0，4–5k）、D（seed 1，4–5k）。数据：[`results/stage2_summary.json`](results/stage2_summary.json)（每格、每条 rollout 和各项汇总）。

32 格全部完成，梯度核对全部通过（第二阶段核对标准见第 4 节；GPU 相对 L2 最大 0.0289，余弦最小 0.99959；每格门控样本另在本地 fp32 下复核，C、D 的 16 个最大相对 L2 为 5.8e-6）。两种表示的峰值已分配显存在每格内相差不到 0.005 GiB（3–4k 最大 5.54 GiB，4–5k 最大 7.88 GiB）。

“每轮斜率”是按格的最小二乘斜率（每增加 1 轮，速度比增加多少）；按单条 rollout 计算的斜率与之相差不到 0.02。

1. **轮数**：8 组（数据集 × 窗口 × 样本组）中，速度比全部随轮数单调上升，斜率 0.48–0.58／轮。合并 8 格后的中位数：k=2 为 1.30（1.00–1.74），k=4 为 2.05，k=6 为 3.17，k=8 为 4.38（3.95–5.18）。逐条 rollout 的范围是 0.92–6.33；低于 1 的只出现在 k=2、token 比接近 1 的 SWE-smith 样本上，是测量噪声的量级。
2. **数据集**：相同轮数和窗口下，nebius 的速度比高于 SWE-smith，差距在少轮时最大：k=2 时 nebius / SWE-smith 为 1.42–1.74 倍，k=8 时为 1.08–1.31 倍（4–5k 窗口的 k4、k6 在 seed 0 中几乎相同，为 0.96–0.99）。两数据集速度比之比与处理 token 比之比基本同步（例如 seed 0 3–4k k2：1.74 对 1.61），也就是说，数据集差异来自每轮重复处理的历史多少（nebius 的系统提示较长，少轮时占比更高），没有超出 token 比能解释的部分。
3. **窗口**：SWE-smith 在 3–4k 与 4–5k 之间基本没有差别（4–5k / 3–4k 为 0.95–1.28，多数在 1 ± 0.05）；nebius 在 4–5k 窗口下较低（0.69–0.99），处理 token 比也同步较低（0.80–0.99）。所以窗口效应同样通过 token 比体现，与第一阶段“长度本身不是主因”一致。注意：不同窗口来自不同会话，只比较会话内的速度比，不比较绝对秒数（见下面的局限）。
4. **机制**：速度比与处理 token 比的相关系数，按 192 条 rollout 为 **0.987**（SWE-smith 0.993，nebius 0.982），按 32 格为 0.996；与轮数为 0.949。速度比 / token 比按格为 0.74–0.95，中位数 3–4k 为 0.835、4–5k 为 0.821（第一阶段 2–4k 为 0.87、4–6k 为 0.81）；逐条回归斜率为 0.82。在长度固定时，“轮数 → token 膨胀 → 耗时”仍然成立，而且合并的时间收益仍略低于 token 收益。
5. **可重复性**：seed 0 与 seed 1 是完全不重叠的两批样本，16 对对应格的速度比相对差中位数为 **6.1%**，最大 15.1%（SWE-smith 3–4k k4：1.62 对 1.86）；8 条轮数曲线都单调，斜率 0.48–0.58。同一样本组在 C 首次运行与重跑之间，已完成的两格速度比相差不到 1%（1.065 / 1.054，2.062 / 2.067）。

### 3.5 第三阶段：长上下文 6k–16k（18 格，107 条）

先跑核心 11 格（会话 A、B），看过结果后再补跑 k = 6 的 7 格（会话 K6）。三次会话都使用 Kaggle 预装的 torch 2.11.0+cu128。判定规则在运行前固定。数据：[`results/stage3/`](results/stage3/)，其中 `summary.json` 含每格结果、判定和逐条 rollout 的耗时比、token 比与平方成本比，其余文件是各次会话的原始 `results.json`。

**计算路径**：为了在 T4 上跑到 16k，换了一条新的计算路径。
- 显式复制 KV 头，强制使用 memory-efficient SDPA 内核，不再物化 L² 注意力矩阵；
- 只在监督位置计算 logits。

这两处改动不改变 loss 和梯度：CPU fp32 上对真实模型核对过，梯度相对 L2 为 1.1e-6；GPU 门控核对 18 格全部通过（相对 L2 ≤ 0.029，cosine ≥ 0.9996）。但改动改变了成本结构，所以**本节数字只在本节内部比较**，不和第一、二阶段直接比较。

pilot 中同一条 4–6k 样本上，新路径的峰值显存为 2.95 GiB，旧路径为 7.56 GiB；transition 和 trajectory 的耗时分别快 3.8 倍和 5.1 倍（含预热，只做粗略比较）。

两次重复的速度比相差都不超过 0.5%，只有 SWE-smith 6–8k k4 为 4.8%。k = 6 来自另一次会话；比较的都是会话内的速度比，不比较绝对秒数。

**按事先固定的规则**：
1. **Q1 长度**：五组的速度比对窗口中点的斜率都是负的，判定为“**速度比随长度下降**”。每 1k token 的斜率为：SWE-smith k4 −0.031、k6 −0.083、k8 −0.034；nebius k6 −0.004、k8 −0.203。需要注意三点：
   - 效应很小，而且多数组不单调。从 4–6k 到 12–16k，SWE-smith 的降幅为 17%（k4）、19%（k6）和 8%（k8）。
   - nebius k6 基本持平（3.31 / 2.77 / 3.23）。
   - nebius k8 降幅较大（4.29 → 3.27），但它的 token 比也从 5.07 降到 4.13，主要是 token 膨胀变小；SWE-smith k6 也一样，token 比从约 3.9 降到约 3.35。
2. **Q2 机制**：
   - 速度比 / token 比有 3/5 组随窗口单调下降，判定为“**合并收益相对 token 收益随长度递减**”。四个窗口的中位数依次为 0.89、0.85、0.86、0.84；SWE-smith k6 从 0.909 降到 0.849，k8 从 0.894 降到 0.840。
   - 逐条拟合“速度比 = a × token 比 + b × 平方成本比”，平方项权重从 0.43（4–6k）、0.48、0.60 升到 0.70（12–16k），token 项权重相应从 0.56 降到 0.29。这与预测一致：越长，注意力的平方成本占比越高，收益越向平方成本比靠近。
   - 速度比与 token 比的逐条相关系数为 0.990（107 条）。
3. **Q3 轮数**：7 个“数据集 × 窗口”组合中，速度比都随 k 单调上升。SWE-smith 为 k4 约 1.8–2.1、k6 约 2.9–3.5、k8 约 4.1–4.6。nebius 8–12k 的 k6 和 k8 很接近（3.23 对 3.27），因为两者的 token 比也接近（3.81 对 4.13）。

**峰值显存**主要跟着单行中 policy token 的最大数量走，而不是上下文长度。SWE-smith 8–12k k8 中有一行有 3,366 个 policy token，这一格的峰值（7.51 GiB）因此最高。归因是推断：只在监督位置计算的 logits 及其 fp32 副本随 policy token 数线性增长，没有做 profile。16k 上下文的格峰值都不超过 4.7 GiB。

**资源**：pilot 6.75 GPU 分钟，A、B、K6 三次会话合计约 131 分钟。

## 4. 工程过程中的发现

这些问题都在 GPU 上真实出现过，每一个都先在本地复现或测出原因，再修复（失败的运行不自动重试）：

| 现象 | 原因 | 修复 |
|---|---|---|
| 创建 venv 时 ensurepip 失败 | Kaggle 的 Python 3.13.15 没有 `ensurepip` 模块；`venv` 还会吞掉它的底层错误 | `--without-pip` 并复用系统 pip，加上解释器与 pip 的诊断 |
| `pip check` 失败 | `--system-site-packages` 会检查整个镜像，报出 6 条与运行无关的冲突 | 只对运行依赖闭包内的冲突判失败 |
| 注入 LoRA 时 ImportError | 镜像预装的 torchao 0.10.0 低于 PEFT 0.21.2 的要求 | 固定 torchao 0.17.0（官方标明兼容 torch 2.11），并在下载权重前用微型模型做离线 LoRA 预检 |
| 梯度核对时 CUDA OOM | 核对调用 `model.eval()`，而 HF 只在 training 模式下做梯度检查点；加上 math 内核物化注意力矩阵 | 核对改用 training 模式并强制 dropout 为 0；真实模型上核对阶段保存的激活从 7.93 GB 降到 0.19 GB |
| 6k token 时梯度核对未通过 | 不做 loss scaling 时 fp16 梯度下溢（相对 L2 最大 0.038）；scale 256–65536 时降到 ≤0.0113 | 核对使用 loss scale 4096，并改用相对 L2、余弦、loss 相对误差作为标准，逐元素检查只作诊断 |
| 第二阶段 4–5k 门控核对未通过（运行 C） | 单个样本的 fp16 梯度误差波动较大：SWE-smith k6 的相对 L2 为 0.0242、余弦 0.99971，略超第一阶段标准；同一样本在 CPU fp32 下相对 L2 为 3.9e-6 | GPU 门槛改为相对 L2 ≤0.05、余弦 ≥0.999（loss 门槛 ≤1e-3 不变），并在提交前用 CPU fp32 核对每格门控样本（C、D 共 16 个，全部通过）；C 整体重跑 |
| 第三阶段：16k 上下文在 T4 上不可行 | 默认路径以 `enable_gqa=True` 调用 SDPA，T4 上退回 math 内核，物化 L² 注意力矩阵；同时对整行计算词表 logits | 显式复制 KV 头并强制 memory-efficient 内核（内核不可用时直接报错）；只在监督位置计算 logits。CPU fp32 上核对新旧路径梯度一致（相对 L2 1.1e-6） |
| 第三阶段：提交时 Kaggle 返回 HTTP 400 | 打包后的脚本有 1.34 MB（此前成功提交的最大约 401 KB）。长上下文每一轮都重复此前的全部上下文，超出 DEFLATE 的 32 KiB 窗口，几乎压缩不了 | data.json 改用 LZMA 压缩（脚本降到约 310 KB），打包时拒绝超过 450 KiB 的脚本 |

新核对标准的依据：本地 fp32 下，正确样本的相对 L2 约 1e-6；改动 1 个上下文 token 时为 0.044（余弦 0.99905，loss 相对误差 3.0e-3）；改动 1 个目标 token 时为 0.156。T4 fp16 加 loss scaling 时噪声上限为 0.0113（余弦 ≥0.99994）。第一阶段的阈值设在两者之间。

第二阶段的修订：4–5k 时 fp16 噪声达到 0.0289（余弦 0.99959），所以把梯度阈值提到 0.05／0.999。代价是改动 1 个上下文 token（0.044／0.99905）在梯度指标上不再被拒绝，只靠 loss 阈值拒绝（3.0e-3 > 1e-3），再加上逐 token 的数据审计和提交前的 fp32 核对（正确样本约 1e-6）。在 32 个门控样本中，按旧标准只有 2 个不通过（C 的 SWE-smith k6 和 nebius k2）。

## 6. 结论

1. 在本设置下，合并失败、退化为逐轮表示时，训练耗时是合并表示的 **1.5–4.2 倍（按格）**，单条 rollout 最高 5.1 倍。
2. 差距几乎完全由处理 token 的膨胀决定，而膨胀主要来自**轮数**：2 轮时中位数约 1.6 倍，7–10 轮时中位数约 3.5–4.7 倍。上下文长度本身不是主因。
3. 合并的实际时间收益略低于 token 收益，且随长度降低（约 0.97 → 0.81）。
4. 两种表示的峰值显存基本相同，所以合并解决的主要是时间成本，而不是显存上限。
5. **第二阶段（固定长度窗口）确认轮数是主要因素**：长度固定在 3–4k 或 4–5k 时，速度比随轮数单调上升，从 k=2 的约 1.0–1.7 到 k=8 的约 4.0–5.2，斜率约 0.5／轮；两批独立样本的结果一致（格间相对差中位数 6%）。数据集和窗口的差异都可以由处理 token 比解释（相关系数 0.987，192 条）。
6. **第三阶段（4k–16k，新计算路径）**：轮数仍是决定性因素，SWE-smith 为 k4 约 1.8–2.1、k6 约 2.9–3.5、k8 约 4.1–4.6，7 个组合都随 k 单调上升。长度增加时速度比略有下降，合并收益相对 token 收益从约 0.9 降到约 0.8，平方成本的权重随长度上升，与注意力平方项的机制一致。新路径在 16k 时峰值显存不到 5 GiB。

## 7. 局限

- 每格只有 6 条、单种子、两次重复、单张 T4；逐条 rollout 的分析是描述性的，没有做显著性检验。
- 样本是轨迹前缀片段，按层选择时轮数与数据集、层存在混杂（例如 SWE-smith、Toucan 的长层多数只有 2–3 轮）。
- 第一、二阶段只覆盖 ≤6144 token。第三阶段换了计算路径后覆盖到 16k，但只有单个种子、每格 6 条（nebius 8–12k k6 为 5 条）；12–16k 只有 SWE-smith，nebius 没有 k4。长度效应很小且多数组不单调，判定只是描述性的。
- 只测了 Qwen3-0.6B + LoRA；结论不能外推到更大的模型、全参数、分布式训练，以及使用 FlashAttention 等内核的硬件。
- 计时包含有限性检查等校验同步，是带校验的参考训练循环，不代表所有生产训练栈。
- 只评价成本，不涉及学习效果（属于 P3-B）。
- 第二阶段：每格 6 条、两个样本组、每次运行一个会话；不同会话之间 GPU 速度可相差约 30%，所以只比较会话内的速度比，跨窗口、跨样本组的绝对秒数不可比。只覆盖 SWE-smith 与 nebius、2–8 轮、3–5k；Toucan 的多轮样本太少，未纳入。
- 第二阶段放宽了 GPU 门控的梯度阈值（见第 4 节），等价性的严格保证改由数据审计和每格门控样本的 fp32 核对提供；fp32 核对只覆盖每格的首条样本（与 GPU 门控相同），C、D 做了，A、B 没有做（A、B 的 GPU 门控满足旧标准）。
