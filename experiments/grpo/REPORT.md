# P3-B 报告：多轮工具调用 GRPO 中采集方式与训练数据来源的对比

> 所有数字都来自 Kaggle 2×T4 上的真实运行。数据在 [`results/`](results/)，每次运行一个目录（`settings.json`、每步记录 `steps.jsonl`、评测 `evals.jsonl`，其中保存了每个评测任务的回答和奖励）。`python -m experiments.grpo.analyze --out results/summary.json` 按下面的判定规则重新生成 [`results/summary.json`](results/summary.json)。

## 1. 研究问题

前面的实验回答的是数据和成本层面的问题。P3-B 把两条采集链路接进真实的多轮工具调用 GRPO 训练，回答三个问题：

- **Q1 成本（确认性）**：真实 GRPO 训练中，合并样本相对逐轮样本的加速，是否与 P3-A 的成本基准一致？
- **Q2 采集方式对学习的影响**：两条链路下，学习曲线和训练成本有什么不同？
  - **TITO**：`/v1/completions` 直接传 token id，整条轨迹合并为 1 个训练行；
  - **服务端重渲染**：`/v1/chat/completions` + 补丁 v2 模板，按前缀合并，合并失败处拆行。
- **Q3 非规范切分会不会被训练强化**：TITO 上下文会让模型延续自己的非规范切分（见 `experiments/tito_vllm/REPORT.md`）。RL 会强化高奖励轨迹里出现过的 token 序列，那么 TITO 下非规范切分率会不会随训练上升？

后来补充了 **D 组（只保存文本日志）**：rollout 与 C 组（重渲染）完全相同，训练时把对话文本重新渲染、重新分词，训练 token 不一定是采样 token。它回答 Q4–Q6，见第 6 节。

不回答模型在真实 Agent 任务上的能力：环境是自建的轻量可验证环境，结论只限于这个环境。

## 2. 设置

| 项目 | 设置 |
|---|---|
| 环境 | `env.py`，只用标准库。每个任务有一张随机库存表，模型要通过 `lookup(item)` 查单价和库存、`calculate(expression)` 做四则运算（`ast` 安全求值），最后回答 `ANSWER: <总价>`；库存不足时回答 `ANSWER: INSUFFICIENT <物品> <实际库存>`。精确匹配得 1 分，不使用模型判分。工具结果由环境实时返回，严格同策略 |
| 难度 | 每个任务 3 种物品（k = 3），由 pilot2 的基线结果按事先固定的规则选出 |
| 模型 | Qwen3-0.6B（revision 固定），关闭思考，补丁 v2 模板 |
| 适配器 | LoRA r=16、alpha=32，作用于 q/k/v/o；fp16 autocast + GradScaler，梯度检查点 |
| 算法 | GRPO：每个任务 8 条轨迹，优势 = 组内奖励减组均值（不除以标准差）；每批只更新一次，严格同策略，不需要比率裁剪；不加 KL 项 |
| 损失 | 每个 policy token 的 −A·log π，按整批的 policy token 总数归一化；工具观察和 prompt 不参与损失。训练行由 `trace2batch.core.build_samples` 生成 |
| 规模 | 60 步 × 每步 8 个任务 × 8 条轨迹；学习率 1e-5；TITO 和重渲染各 2 个种子，共 4 次运行、15,360 条 rollout |
| 评测 | 固定的 200 个 held-out 任务（种子与训练不重叠），第 0 / 20 / 40 / 60 步评测，T = 1.0；其中 158 个总价任务、42 个缺货任务 |
| 硬件 | Kaggle 2×T4：GPU0 运行 vLLM 0.32 做 rollout，GPU1 训练 LoRA；每步把 adapter 存盘，再通过 `/v1/load_lora_adapter` 热加载到 vLLM |
| 运行顺序 | 种子 0 先 TITO 后重渲染，种子 1 反过来，以抵消先后顺序的影响 |

每步记录的诊断：奖励（按答案类型分开）、每轮非规范切分率、训练行数和 token 数、rollout 与训练耗时，以及 vLLM 采样 logprob 与训练端重算 logprob 之差。每 10 步把同一批数据再按逐轮表示做一次前向加反向（不更新），记录耗时，并核对两种表示的梯度（固定 loss scale 4096，沿用 P3-A 的阈值：相对 L2 ≤ 0.05、cosine ≥ 0.999）。

## 3. 事先固定的判定规则

- **学习效果**：第 60 步相对第 0 步的 held-out 成功率提升，按评测任务做配对 bootstrap（10,000 次），95% 置信区间整体大于 0 才算“学会了”；同时看总体和按答案类型的结果。
- **Q2**：每组只有 2 个种子，只做描述性比较。
- **Q3**：对每次运行的“每轮非规范切分率 ~ 训练步数”做线性回归。TITO 两个种子的斜率都大于 0，且都大于重渲染两个种子的斜率，才报告为“TITO 下训练强化了非规范切分”；否则报告为“60 步内没有观察到强化”。

## 4. pilot：发现并去掉奖励捷径

- **pilot**（TITO，10 步）：可行性没有问题（adapter 热加载可用，单步约 32 s，logprob 差异中位数为 0），但发现了奖励捷径。当时 30% 的任务答案是 `INSUFFICIENT`，基础模型几乎不调用工具就直接回答 `INSUFFICIENT`：基线中缺货任务 49/54 正确，数值任务只有 1/146 正确。总成功率 0.30 → 0.40 掩盖了行为上的巨大变化。
- **修订**（运行前确定）：
  - 缺货答案必须写出物品和实际库存，不查询就无法作答；
  - 评测和每步记录都按答案类型分别统计；
  - Q1 梯度对照加入固定 loss scale 4096。原来 fp16 反向会下溢，第 5 步误报不一致（cosine 0.984）。
- **pilot2**（20 步）：
  - 去掉捷径后，基线总体成功率为 2.5%，各难度都低于 10%，按规则选择成功率最接近 0.4 的 k = 3；
  - 第 0 步 8 组中有 3 组同时有成功和失败的轨迹，有学习信号；
  - 评测成功率在第 10 步达到 0.47，修复后的 Q1 对照通过。

## 5. 结果

4 次运行都跑满 60 步，都有第 60 步的评测；rollout 没有出现请求错误（每次运行 3,840 条，只有达到轮数上限或没有作答两种非正常结束）。

### 5.1 学习效果

| 运行 | 成功率（第 0 → 20 → 40 → 60 步） | 提升 [95% CI] | 总价任务（第 0 → 60 步） | 缺货任务 |
|---|---|---|---|---|
| TITO，种子 0 | 0.07 → 0.675 → 0.77 → 0.78 | +0.71 [0.645, 0.77] | 0.089 → 0.987 | 0 → 0 |
| TITO，种子 1 | 0.065 → 0.66 → 0.775 → 0.785 | +0.72 [0.66, 0.785] | 0.082 → 0.994 | 0 → 0 |
| 重渲染，种子 0 | 0.03 → 0.68 → 0.785 → 0.78 | +0.75 [0.69, 0.81] | 0.038 → 0.987 | 0 → 0 |
| 重渲染，种子 1 | 0.03 → 0.665 → 0.77 → 0.775 | +0.745 [0.685, 0.805] | 0.038 → 0.981 | 0 → 0 |

- 4 次运行的总体提升和总价任务的提升，置信区间都整体大于 0：**两条链路都学会了，学得一样好**。
- **缺货任务一直是 0，没有学会。** pilot2 中可以看到原因：第 0 步模型会尝试写缺货答案，但把所有物品都列出来，严格判分下得 0 分；之后策略收敛到占多数（79%）的总价答案。
- 第 0 步两组都用基础模型，成功率却不同（0.07 / 0.065 对 0.03），说明两种接口之间存在随机差异和接口差异。

### 5.2 Q2：训练成本

| 运行 | 每条 rollout 的训练行数 | 全部行的 token | 参与更新的 token | 训练更新耗时 | rollout 耗时 | 60 步总耗时 |
|---|---:|---:|---:|---:|---:|---:|
| TITO，种子 0 | 1.00 | 2.38M | 0.74M | 569 s | 1,924 s | 2,803 s |
| TITO，种子 1 | 1.00 | 2.48M | 0.80M | 638 s | 2,408 s | 3,368 s |
| 重渲染，种子 0 | 2.07 | 4.13M | 1.23M | 971 s | 1,682 s | 2,978 s |
| 重渲染，种子 1 | 2.05 | 4.09M | 0.99M | 793 s | 1,780 s | 2,907 s |

- 同样的学习效果下，重渲染参与更新的 token 多 **1.23–1.66 倍**，训练更新耗时多 **1.24–1.71 倍**（两个种子分别比较）。
- **TITO 的优势只在训练端。** 本实现中 TITO 每轮多一次 `/tokenize` 请求，而且撞到轮数上限的 rollout 更多（22 / 68 条，重渲染为 0 / 0），所以 rollout 更慢；60 步的总耗时，种子 0 是 TITO 更快，种子 1 是重渲染更快。

### 5.3 Q3：非规范切分没有被强化

| 运行 | 斜率（每步） | 前 10 步均值 | 后 10 步均值 |
|---|---:|---:|---:|
| TITO，种子 0 | −0.00016 | 2.5% | 1.2% |
| TITO，种子 1 | −0.00044 | 3.2% | 0.7% |
| 重渲染，种子 0 | −0.00064 | 3.6% | 0.4% |
| 重渲染，种子 1 | −0.00011 | 3.1% | 2.3% |

四个斜率都是负的，按规则判定为“**60 步内没有观察到强化**”。非规范切分率在两种链路下都随训练下降。

### 5.4 Q1：合并样本的加速与 P3-A 一致

- 每 10 步的梯度对照都通过：TITO 的 cosine ≥ 0.999、相对 L2 ≤ 0.038，重渲染的 cosine 约为 1.0（重渲染每条 rollout 本来就拆成约 2 行，两种表示的差别较小）。
- 逐轮 / 合并的耗时比与 token 比同步变化：TITO 为 2.10–3.35 倍对 2.04–3.09 倍，重渲染为 1.03–1.49 倍对 1.06–1.53 倍，与 P3-A 的结论一致。
- 有两步（TITO 种子 1 第 50 步、重渲染种子 1 第 30 步）所有组的奖励都相同，没有可比较的行，对照记录为空。这是正常情况，不是故障。

### 5.5 训练与推理的数值一致性

vLLM 采样 logprob 与训练端重算 logprob 之差：4 次运行每步中位数的中位数都是 0，单个 token 的最大差为 0.10–0.15 nat。

## 6. D 组：只保存文本日志、训练时重新分词

很多训练栈不保存 token，只保存 OpenAI 格式的对话文本，训练时再用 chat template 渲染、重新分词，并按助手消息的位置生成 mask。这样每条轨迹天然合并为 1 行，代价是训练 token 不一定是模型采样的 token，也就是真正的训练与推理不一致。D 组模拟这种做法：

- **rollout**：与 C 组完全相同（`/v1/chat/completions` + 补丁 v2，同样的任务流、种子和评测集）。C 组复用第 5 节的结果，不重跑。
- **训练行**：rollout 结束后，用服务端 `/tokenize`（v2 模板）渲染“到第 i 条助手消息为止”的对话，减去这一轮的 prompt，截到 `<|im_end|>` 为止，作为第 i 轮的 response，再交给同一个 `build_samples`。
- **每轮比较训练 token 与采样 token**：match 相同；retoken 文本相同但切分不同；text 文本不同；prefix_failed 渲染结果不以 prompt 开头。
- 其他设置（GRPO、LoRA、60 步、评测）与 A、C 组相同。每个种子单独一次会话。

### 6.1 事先固定的规则

- **Q4 不一致会不会伤害学习**：每个种子对 200 个评测任务做配对 bootstrap，计算第 60 步“D 成功率 − C 成功率”。两个种子的 95% CI 上界都 < 0，判定为“伤害”；下界都 > 0，判定为“有帮助”；否则判定为“60 步内没有检测到差异”。
- **Q5 成本**：与 A、C 组做描述性比较。
- **Q6 非规范切分**：D 两个种子的斜率都小于 C 两个种子的斜率，才判定为“D 下下降得更快”。

### 6.2 结果

两次运行都健康：
- 冒烟测试通过，跑满 60 步，都有最终评测；3,840 条 rollout 全部正常作答；
- 文本日志重建 0 次 prefix_failed；
- 梯度对照全部通过（cosine ≥ 0.9998）；
- 一致轮的 logprob 差异中位数为 0。

| | D，种子 0 | D，种子 1 | C，种子 0 / 1 |
|---|---|---|---|
| 成功率（第 0 → 20 → 40 → 60 步） | 0.03 → 0.725 → 0.775 → 0.78 | 0.03 → 0.705 → 0.77 → 0.78 | 0.03 → … → 0.78 / 0.775 |
| 提升 [95% CI] | +0.75 [0.69, 0.81] | +0.75 [0.69, 0.81] | +0.75 / +0.745 |
| 第 60 步 D − C [95% CI] | 0.000 [−0.015, +0.015] | +0.005 [0.000, +0.015] | — |
| 每条 rollout 的训练行数 | 1.00 | 1.00 | 2.07 / 2.05 |
| 参与更新的 token | 0.56M | 0.45M | 1.23M / 0.99M |
| 训练更新耗时 | 416 s | 329 s | 971 s / 793 s |
| 60 步总耗时 | 2,124 s | 2,117 s | 2,978 s / 2,907 s |
| 非规范切分率斜率（每步） | −0.00052 | −0.00038 | −0.00064 / −0.00011 |
| 训练 token ≠ 采样 token 的轮次 | 30.9% | 32.1% | — |

（两个 D 种子是独立的运行：第 60 步评测在 2 个任务上结果不同，只是成功的总数恰好相同，所以提升和 CI 也相同。）

- **Q4：60 步内没有检测到差异。** 两个种子的差值都接近 0，CI 都包含 0（种子 1 的下界正好是 0）。
- **Q5：D 是三组中训练最便宜的。** 每条轨迹 1 行，参与更新的 token 比 C 少 54%–55%，甚至比 A 少（A 为 0.74M / 0.80M），原因见下面不一致的来源。
- **Q6：没有差异。** D 的斜率并不都小于 C（C 种子 1 的斜率是 −0.00011，但 C 种子 0 是 −0.00064）。

### 6.3 不一致的规模与来源

- 训练 token 与采样 token 不同的轮次占 **31%–32%**：几乎全部是 text 类（3,449 / 3,583 轮），retoken 类只有 8 / 11 轮。
- **方案在运行前的估计是约 2%，这个估计是错的**：它只用 C 组的非规范切分率（1.4%–1.8%）来估，漏掉了文本层面的改写。事后看，C 组每条轨迹拆成约 2.06 行，本来就说明文本改写很常见。
- **来源**（本地复现）：在 CPU 上用 Qwen3-0.6B 对 12 个难度 3 任务的第一轮采样（T = 1.0），用客户端 Hermes 解析并按 v2 重渲染，9 条与原文不同。全部是模型在同一条消息里、工具调用之后又写了内容，例如提前写出的 `ANSWER: ...`，或者格式错误的多余工具调用。Hermes 解析器只保留第一个工具调用之前的正文和解析成功的工具调用，之后的文本被丢掉。所以 D 组训练的是“清理过”的消息，这也是 D 参与更新的 token 最少的原因。
- “不同 token 的比例”（27%–31%）是逐位置比较的：一处删除之后的所有位置都算不同，所以偏高，只作为上界。
- 不一致轮的整轮 logprob 之差，每步中位数的中位数为 4.8 / 5.3 nat。两边的 token 数不同（尾部文本被删掉），这个数字只说明“训练的序列与采样的序列差别很大”，不能当作逐 token 的偏差。

### 6.4 探索性观察（不在事先固定的规则里）

| 训练步 | 0–4 | 5–9 | 10–19 | 20–29 | 30–39 | 40–49 | 50–59 |
|---|---:|---:|---:|---:|---:|---:|---:|
| D 种子 0：不一致轮次比例 | 45.6% | 37.4% | 35.6% | 35.4% | 34.2% | 24.2% | 16.4% |
| D 种子 1：不一致轮次比例 | 44.5% | 35.6% | 34.6% | 32.9% | 32.0% | 30.6% | 24.2% |
| C 种子 0：每条 rollout 的行数 | 1.98 | 2.10 | 2.07 | 2.07 | 2.09 | 2.06 | 2.07 |
| C 种子 1：每条 rollout 的行数 | 1.97 | 2.07 | 2.08 | 2.04 | 2.05 | 2.04 | 2.05 |

两个种子中，D 的不一致比例都随训练明显下降，而 C 每条轨迹的行数（反映同一种文本改写）基本不变。一种解释：D 只在“工具调用后立即结束”的消息上训练，模型学会了在工具调用后停止；C 训练的是带尾部多余文本的原始输出，而尾部文本不影响奖励，所以一直保留。这是事后观察，没有事先固定规则，也没有直接统计模型输出中的尾部文本，只作为假设。

## 7. 结论

1. 在这个环境中，TITO 和服务端重渲染两条链路学得一样好（第 60 步成功率都约为 0.78，总价任务约 0.98–0.99）。
2. 代价在重渲染一侧：每条 rollout 拆成约 2 行，训练更新多花 24%–71% 的时间。TITO 的 rollout 端在本实现中更慢，所以端到端时间没有一致的优势。
3. TITO 会让模型延续自己的非规范切分，但 60 步的 GRPO 训练没有强化这种倾向；两种链路下非规范切分率都随训练下降。
4. 真实 GRPO 中合并样本的加速与 P3-A 的成本基准一致：耗时比跟着 token 比走。
5. 只保存文本日志、训练时重新分词（D 组）：约 31% 的轮次训练的不是模型采样的 token，主要是解析器丢掉了工具调用之后的文本；但 60 步内学习效果与 C 组没有可检测的差异，而且训练成本是三组中最低的。探索性地看，D 训练会让这种不一致随训练减少。

## 8. 局限

- 环境是自建的轻量任务，离真实 Agent 任务较远；模型只有 0.6B，结论只限于这个设置。
- 每组只有 2 个种子，训练 60 步；没有 KL 项；T4 上使用 fp16。
- 缺货任务没有学会，学习效果实际上只体现在总价任务上。
- Q3 的强化效应可能需要比 60 步更长的训练才能显现。
- TITO 与重渲染的 rollout 耗时差异取决于本实现（每轮一次 `/tokenize` 请求），不代表 TITO 本身的开销。
- D 组与 C 组不在同一次会话中运行，vLLM 的采样存在非确定性，只按种子配对比较。D 组的不一致主要来自 Hermes 解析器丢弃尾部文本，结论不能推广到其他解析器或模板。“没有检测到差异”只针对 60 步、这个环境和成功率这一指标。
